Hentronix coop door — traffic route & takeover plan

Keeping the automatic chicken‑coop door working under Home Assistant after Hentronix (UK) ceased trading — with no hardware change.

The short version

The door hardware is fine and keeps running its schedule regardless. What's at risk is the "smart" layer — and that's what this future‑proofs.

The door is a little WiFi gadget that "phones home" over the internet to a message server (an MQTT broker) on a cloud host. The phone app works through that same broker: the app says "open", the broker passes it to the door; the door reports its battery, the broker passes it to the app. With Hentronix shut down nobody is clearly answerable for that server, and it could go dark at any time. If it does, dawn and dusk carry on regardless, because they run on the door's own built‑in clock (RTC) and battery. But the app, remote control, schedule changes and battery readings all stop.

The good news: the door talks to the broker in plain, unencrypted messages, aimed at a fixed internet address baked into its firmware. That lets you add one rule on your router that intercepts those messages and redirects them to your own broker at home — a small always‑on server running Home Assistant. The door can't tell the difference; it uses the same login and the same messages. From then on the coop is driven entirely from the house — no cloud, no vendor, no internet dependency — and you get your own app for control and monitoring.

Why change it

  • The vendor is gone. Hentronix (UK) has ceased trading; the app is maintained by a single developer. If the app is pulled or stops being updated, the WiFi features die.
  • Everything hangs on one cloud server. Control, scheduling and battery/status monitoring all route through <BROKER_IP>, a single broker with no redundancy. Nobody is clearly responsible for it now (possibly the electronics supplier, possibly nobody). If it goes offline, the smart features go with it.
  • The door hardware is fine; the cloud layer is what's at risk. Dawn/dusk runs locally on the door's built‑in clock (RTC) and battery, so it doesn't need the cloud. What you'd lose is remote control, schedule changes and monitoring.
  • The design makes a clean rescue possible. Plaintext MQTT to a hardcoded IP means we can redirect it locally with no DNS spoofing, no TLS to break, and no change to the hardware or firmware.
  • Local ownership. Home Assistant keeps the coop working indefinitely, privately, with no dependence on a defunct company's servers.

How it was worked out

The method used on one unit — all read‑only. The door's traffic was watched; no command was ever sent to it. You can repeat the same steps on your own device.

1 · Researched the company & app Hentronix (UK) has wound down; the "Hentronix WiFi" app is a single‑developer app, and the company website is just a marketing page — no cloud of their own under that name.
2 · Got onto the network with the door Reached the home network the opener lives on (a Linux box on the same network is enough as a vantage point for the capture).
3 · Located the door Found the opener's IP on the network. It often sits on a separate "smart‑devices" (IoT) VLAN; a healthy neighbour device confirms that VLAN is reachable.
4 · Found it asleep, with no open ports The door is battery/solar and sleeps to save power. It answered only occasionally and had no open "ports" — so the app doesn't connect to it; the door must reach out to something.
5 · Ruled out a vendor‑named cloud No broker hostnames existed under the vendor's domain. So it talks to a third‑party server, or a fixed address baked into the firmware.
6 · Watched its traffic at the gateway A passive capture caught the door connecting out to a cloud server on <BROKER_IP> : 1883 in plain, unencrypted MQTT, every ~16 seconds — straight to a hardcoded IP, no DNS.
7 · Read the whole conversation ✓ Decoded its login, device ID, and the two channels it uses (one to report status, one to receive commands). No encryption, no secret handshake — exactly what makes a local takeover simple.
8 · The plan Because it talks plainly to a fixed address, one router rule can send it to a broker on your own server instead — no change to the door. That's the plan below.

The plan

  1. Learn the codes manually from the app (do this first)While the vendor cloud is still up, run a passive capture while you work through the real app at the coop: open, close, then change each setting once (open/close times, light, motor firmness). Each press arrives on /hentronix/app/ as a command, and the result shows on /hentronix/dev/ as state, so one session gives you both. It must happen before the switchover, because once traffic is redirected the app can no longer reach the door.
  2. Stand up the broker + Home AssistantOn an always‑on server: Home Assistant + the Mosquitto add‑on, static <HA_IP>. Configure Mosquitto to accept the door's captured login (<MQTT_USER> / <MQTT_PASS>) and the /hentronix/# topics, keeping retained messages.
  3. Build the Home Assistant controlsSensors from /hentronix/dev/<DEVICE_ID> (battery, door state, uptime), plus an HA cover and settings that publish the captured JSON, retained, to /hentronix/app/<DEVICE_ID>. Only codes seen from the real app, never guesses.
  4. Switch over: add the router redirect (DNAT)A destination‑NAT rule: source <DOOR_IP>, destination <BROKER_IP> port 1883 → <HA_IP>:1883, plus a firewall allow for the door's VLAN → <HA_IP>:1883. If the server sits on the same VLAN as the door, it also needs a masquerade (SNAT) so replies come back through the gateway. The door targets a fixed IP, so this keeps working even after the vendor's server disappears.
  5. Supervised first test, then retire the appFirst open/close through Home Assistant is done deliberately, with someone watching the coop. Dawn/dusk keeps running on the door's own clock throughout, so the hens are never without their schedule during the changeover.
Captured facts behind the plan (from one unit): plaintext MQTT 1883no TLS / no pinning hardcoded IP (no DNS)reconnects ~16s retained commands
Time‑sensitive: step 1 only works while the vendor cloud is still up, because the real app has to send the commands. If the cloud dies first, you lose the clean source of the codes — do that session early.
